# 崩溃排查与中断规范（FreeRTOS / H7）

> 这份文档对应一次"为什么老是卡死、卡死又没有任何提示"的整治。
> 看完你应该能做到：**板子再卡死时，串口上一定有话说，而不是一片安静。**

---

## 一、为什么以前会"静默卡死"

| 现象 | 根因 | 现在的做法 |
|---|---|---|
| 卡死，串口一个字没有，也没有 HardFault 迹象 | `HardFault_Handler` 里只有 `while(1)` | 改成 naked 汇编取栈帧 → `BSPFaultDump()` 打印 PC/LR/CFSR，再停机 |
| 初始化某一步失败，板子直接不动 | `Error_Handler()` 是 `__disable_irq(); while(1)` | 改成 `BSPFaultReport("Error_Handler", ...)`，串口会打印 |
| 偶发跑飞/数据错乱，重启又好了 | 任务栈溢出踩坏了相邻内存 | `configCHECK_FOR_STACK_OVERFLOW=2` + `vApplicationStackOverflowHook` 打印任务名 |
| 加设备加到一半就不动了 | 32 KB 堆被 malloc 耗尽，之后解引用空指针 | `configUSE_MALLOC_FAILED_HOOK=1` + `vApplicationMallocFailedHook` |
| 断言失败 → 静默死循环 | `configASSERT` 是 `disable_irq + for(;;)` | 改成打印断言表达式 |
| 串口日志"越打越卡"，最后整机卡顿 | **在中断里**调 `LOGINFO`：`HAL_UART_Transmit` 是阻塞忙等（最长 20 ms），1 kHz 的 CAN 中断里打一行 = CPU 被吃掉 40% | `bsp_log` 增加 `__get_IPSR()==0` 判断：中断里只写 RTT，**不碰串口** |
| CAN 线一松，系统像死了一样 | `HAL_FDCAN_ErrorStatusCallback`（在中断里）里既打日志又 Stop/Start，bus-off 反复发生 → 中断风暴 | 中断里只置标志；恢复动作 + 日志挪到 `CANTransmit()`（任务上下文），并且 100 ms 最多恢复一次 |

## 二、卡死之后怎么看

串口（USART1，115200-8N1）会打印类似：

```
========== BSP FAULT DUMP ==========
cause   : HardFault (ipsr=3)
R0      : 0x00000000  R1 : 0x20000120
R2      : 0x00000004  R3 : 0x0800ABCD
R12     : 0x00000000
LR      : 0x08013A45
PC      : 0x08013A44   <== 出错指令地址
xPSR    : 0x61000000
EXC_RET : 0xFFFFFFFD  (bit2=1 用 PSP / bit4=0 有 FPU 扩展帧)
CFSR    : 0x00008200   PRECISERR BFARVALID
HFSR    : 0x40000000   FORCED
DFSR    : 0x00000000
MMFAR   : 0x00000000
BFAR    : 0xDEADBEEF
MSP     : 0x2001FF80
PSP     : 0x20003F20
IPSR    : 3
------------------------------------
提示: PC 那一行是出错指令, 用
  arm-none-eabi-addr2line -f -e build/Debug/RM.elf 0x08013A44
就能定位到源文件和行号。
====================================
```

### 关键三行

1. **PC**：出错的那条指令。`arm-none-eabi-addr2line -f -e build/Debug/RM.elf <PC>` 直接给文件名+行号。
   （如果 PC 落在 `0x20000000` 附近，说明跳进 RAM 执行了 —— 典型是函数指针被踩坏/野指针。）
2. **CFSR**：fault 的类型。对照下表。
3. **BFAR / MMFAR**：出错时访问的地址。`0xDEADBEEF` 这种一看就是野指针。

### CFSR 位对照（本工程打印的就是这些）

| 位 | 名字 | 含义 | 常见原因 |
|---|---|---|---|
| 0 | IACCVIOL | 取指访问违例 | 跳到不可执行区（MPU） |
| 1 | DACCVIOL | 数据访问违例 | 访问了 MPU 保护区 |
| 3/4 | MUNSTKERR/MSTKERR | 异常出入栈失败 | 栈指针被踩到非法地址 |
| 8 | IBUSERR | 取指总线错误 | 跳到未映射地址 |
| 9/10 | PRECISERR/IMPRECISERR | 数据总线错误（精确/不精确） | **最常见**：野指针、访问已关闭外设、DMA 写到非法地址 |
| 11/12 | UNSTKERR/STKERR | 入栈/出栈总线错误 | 栈溢出（栈顶越界） |
| 16 | UNDEFINSTR | 未定义指令 | 跳进数据区执行、函数指针损坏 |
| 17 | INVSTATE | 状态非法 | 函数指针最低位是 0（跳到 Thumb 之外的地址） |
| 19 | NOCP | 没开 FPU 却用了 FPU 指令 | 上下文保存配置问题 |
| 24 | UNALIGNED | 非对齐访问 | 结构体打包 + 强转 |
| 25 | DIVBYZERO | 除零 | 分母为 0 |

> `HFSR.FORCED=1` 的意思是"有个可配置 fault 被升级成了 HardFault"。这时 CFSR 里一定有具体原因，**先看 CFSR**。

## 三、本工程的中断规矩（照这个写就不会有风暴）

1. **优先级**：所有会调用 FreeRTOS API 的中断，优先级数值必须 **≥ 5**
   （`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`）。本工程 CubeMX 里外设统一给的 5，是对的。
   FreeRTOS 的 SysTick/PendSV 是 15（最低）。
2. **中断里只做三件事**：读数据、清标志、投递消息（`...FromISR`）。
   不做：阻塞延时、打印日志、`malloc`、等外设、解析长报文。
3. **绝对不要在中断里调 `HAL_Delay` / `HAL_UART_Transmit` / `LOGINFO`**。
   本工程已经做了兜底：`bsp_log` 在中断上下文只写 RTT。
4. **不要在中断里做"恢复/重启"这类重活**（如 CAN bus-off 的 Stop/Start）。
   置个标志，交给 1 kHz 的任务做。
5. 中断标志必须清干净（HAL 的 `HAL_xxx_IRQHandler` 一般会清；自己写的 ISR 要确认）。
6. 新增外设后跑一次 `python tools/irq_audit.py`：检查"已使能的中断是否都有 HAL 转发"。
   **漏一个 = 第一次进中断就跳进默认的死循环**，表现和"卡死"一模一样。

## 四、为什么全工程不再用 HAL_Delay

`HAL_Delay()` 的实现是"忙等 `uwTick` 变化"，而 `uwTick` 由 TIM2 中断递增。于是：

- 在 `__disable_irq()` 区域内调用 → **永远不返回**（tick 停了）；
- 在比 TIM2 优先级更高的中断里调用 → 同样永远不返回；
- 在 FreeRTOS 任务里调用 → 白占 CPU，低优先级任务被饿死。

本工程统一用 `DWT_Delay()`（CPU 周期计数器）：

- 关中断照常计时；
- 自带防死等保护（CYCCNT 不计数时最多转一圈就返回）；
- 调度器起来之前也能用（`main()` 里 `SystemClock_Config()` 之后立刻 `DWT_Init()`）。

> 已经改掉的地方：`USBD_LL_Delay()`、`ist8310` 的复位延时、`BoardBeep()`。
> 需要"任务里等一会儿"时，用 `osDelay()`；需要"中断关着也要等"时，用 `DWT_Delay()`。

## 五、怀疑"中断风暴"时的排查顺序

1. **看串口有没有 FAULT DUMP** —— 有的话先按第二节定位，那不是风暴。
2. **确认没有静默断言**：现在断言会打印 `cause : configASSERT` + 断言表达式。
3. **关掉不用的外设**：`bsp/bsp_board.h` 里 `BSP_USB_ENABLE 0`。
   OTG_HS 是 MCU 上最容易"没插线也反复进中断"的外设，排查时第一个关它。
4. **跑 `python tools/irq_audit.py`**：检查是否有"已使能但没写 IRQHandler"的中断。
5. **量一量**：在 `BuzzerTask()`/`DaemonTask()` 里打一次 `DWT_GetTimeline_ms()`，
   若 100 Hz 的任务实际周期明显变长，说明 CPU 被中断吃掉了。
6. **二分法**：把 `RobotInit()` 里注册的模块一个个注释掉，看哪个一加上就卡。
   （本工程 `board_demo.c` 里每个模块都有独立开关，改 `robot_def.h` 即可。）
